## 違いを理解する

何度も出てくる基本要素です。それぞれ、ロードマップの後半で詳しく扱います。

### CLAUDE.md
- **本質:** プロジェクト専用の指示を書いた Markdown ファイル。使う技術、インストール手順、テストの実行方法、コードの書き方のルールなどを記載します。
- **場所:** プロジェクトのルート（`CLAUDE.md`）。すべてのプロジェクトに共通させたい場合は `~/.claude/CLAUDE.md` にも置けます。
- **目的:** 新しいセッションを開くたびに、Claude の記憶は空の状態から始まります。このファイルがあれば、毎回ルールを説明し直さずに済みます。

### コンテキスト
- **本質:** 1 つのセッションで Claude が今「覚えている」すべて。会話、読んだファイル、実行したコマンドの結果を含みます。
- **場所:** 現在のセッションにおける Claude の作業メモリ内。容量には上限があります。
- **目的:** Claude は作業を理解するためにコンテキストが必要です。いっぱいになると古い詳細を忘れやすくなるため、`/compact`（要約）や `/clear`（リセット）を使います。

### モデル
- **本質:** 作業を行う AI モデル。Opus、Sonnet、Haiku、Fable があり、賢さ、速度、コストが異なります。
- **場所:** お使いのパソコンではなく、Anthropic のインフラ上で動きます。`/model` または起動時に選びます。
- **目的:** 作業ごとに適切な「賢さ」を選べるようにするためです。難しい作業には強いモデル、単純な作業には軽いモデルを使うと、利用量を節約できます。

### モード
- **本質:** 確認なしで Claude がどこまで実行してよいかの範囲。例：編集前に確認する、計画のみ（Plan）、自動。
- **場所:** 現在のセッションの設定。`Shift+Tab` で切り替えます。
- **目的:** 安全のためです。特に大切なプロジェクトでは、ファイル編集やコマンド実行をどこまで許すかを自分で決められます。

### ツール
- **本質:** Claude ができる具体的な操作。例：`Read`（ファイルを読む）、`Edit`（ファイルを編集）、`Bash`（コマンドを実行）、`Grep`（コード内を検索）、`WebSearch`（Web を検索）。
- **場所:** Claude Code に組み込まれています。`Bash` と `Edit` は許可を出した後、お使いのパソコン上で動きます。
- **目的:** ツールがなければ Claude は文章で答えることしかできません。ツールがあれば、ファイルを開く、コードを書き換える、テストを実行するといった実際の作業ができます。

### スキル
- **本質:** 繰り返し使う手順を記録した `SKILL.md` を含むフォルダ。例：リリースノートの書き方、マイグレーションの作り方。
- **場所:** プロジェクトの `.claude/skills/`、または複数のプロジェクトで共有するなら `~/.claude/skills/`。
- **目的:** ノウハウを再利用できる形にまとめるためです。スキルは必要なときだけ読み込まれるため、コンテキストを圧迫しません。

### MCP（Model Context Protocol）
- **本質:** Claude を GitHub、データベース、Slack などの外部サービスやデータにつなぐ、オープンな標準規格。
- **場所:** プロジェクトの `.mcp.json` に設定するか、`claude mcp add` で追加します。接続の管理は `/mcp` で行います。
- **目的:** Claude はプロジェクト内のことしか知りません。MCP によって外の世界にも手が届くようになります。例：GitHub の Issue を読む、データベースを検索する。

### プラグイン
- **本質:** スキル、コマンド、サブエージェント、フック、MCP サーバーなどを含められる、セット済みのパッケージ。
- **場所:** マーケットプレイスから `/plugin` でインストールします。お使いのパソコン上の Claude の設定フォルダに保存されます。
- **目的:** 完成した設定一式をすばやく共有・導入するためです。チーム全員が同じ基準を使え、1 つずつ設定し直す必要がなくなります。

### フック
- **本質:** イベントが起きたときに自動で実行されるシェルコマンド。例：Claude がファイルを編集した直後。
- **場所:** `.claude/settings.json` に記述するか、`/hooks` メニューから作成します。
- **目的:** ある作業が必ず実行されることを保証するためです。例：編集のたびにコードを自動整形する。Claude が忘れることもある「ソフトな」指示の `CLAUDE.md` と違い、フックは仕組みとして動くので、Claude の記憶に依存しません。

### サブエージェント
- **本質:** 別の作業を任された補助 AI。例：コードの検索やテストの作成。独自のコンテキストを持ちます。
- **場所:** 各サブエージェントは `.claude/agents/` 内の Markdown ファイルです。
- **目的:** 多くのファイルを検索・読み込むと、メインの会話が埋まってしまいます。サブエージェントに任せれば、メインの会話は簡潔なままで、戻ってくるのは要約だけになります。

最小限の `CLAUDE.md` の例：

```markdown
# Claude 向けプロジェクトメモ

- 技術スタック: Next.js 16, TypeScript, Tailwind
- インストール: `npm install`
- テスト: `npm test`（完了前に必ず通すこと）
- スタイル: 名前付きエクスポートを使う。default export は使わない
```

### 混同しやすいペア

| ペア | 何が違う？ | 身近なたとえ |
| --- | --- | --- |
| **CLAUDE.md – スキル** | CLAUDE.md はセッション開始時に **毎回** 読まれる。スキルはその作業が **必要なときだけ** 読み込まれる。 | CLAUDE.md は入口に貼られたルールで、入る人は全員読む。スキルは棚にしまったマニュアルで、必要なときだけ取り出す。 |
| **コンテキスト – モード** | コンテキストは Claude が今 **覚えている** こと。モードは Claude が確認なしで **自分でやってよい** 範囲。 | コンテキストは社員の記憶。モードはその社員に与える権限。 |
| **モデル – ツール** | モデルは考える **頭脳**。ツールは作業する **手**（ファイルを読む、編集する、コマンドを実行する）。 | 医師がモデル、医療器具がツール。 |
| **MCP – プラグイン** | MCP は GitHub やデータベースなど外部サービスへの **接続口**。プラグインはスキル、フック、MCP などを含む **セット済みパッケージ**。 | MCP はコンセント。プラグインは工具一式のセット。 |
| **フック – サブエージェント** | フックはイベントのたびに **自動で実行されるスクリプト**。毎回必ず動き、AI は考えない。サブエージェントは自分の仕事と記憶を持つ **補助 AI**。 | フックは自動の警報ベル。サブエージェントは仕事を任せた同僚。 |

## どのモデルをいつ使う？

| モデル | 強み | 使いどころ |
| --- | --- | --- |
| **Fable** | 最も高性能、最も深い推論、最も高コスト | 難しい原因調査、アーキテクチャ判断、長時間のエージェント作業 |
| **Opus** | 複雑な作業での高い推論力 | 大規模リファクタリング、難しいバグ、計画 |
| **Sonnet** | 品質・速度・コストのバランス | 日常の機能開発 |
| **Haiku** | 最速かつ最安 | 小さな修正、簡単な質問、軽量なサブエージェント |

```text
/model           # モデル選択画面を開く
/model sonnet    # 直接切り替える
/model fable     # 最も高性能なモデル（どのプランでも既定ではない）
```

<Callout>
まずは既定のモデルで始めましょう。Claude が苦戦したら上位モデルへ、単純な作業や繰り返し作業では下位モデルへ切り替えて利用量を節約します。
</Callout>

## よくある使い方

| 用途 | プロンプト例 |
| --- | --- |
| コードベースを理解する | `フォルダ構成と、リクエストがアプリ内をどう流れるか説明して` |
| バグ修正 | `auth.spec.ts で npm test が失敗します。原因を見つけて直して` |
| テスト作成 | `utils/date.ts の単体テストを追加して。境界ケースも含めて` |
| リファクタリング | `src/legacy のクラスコンポーネントをフックに書き換えて` |
| 依存関係の更新 | `React を最新版に上げて、破壊的変更に対応して` |
| Git 作業 | `ステージした変更のコミットメッセージを書いて` |
| ドキュメント | `ローカルでの実行方法を説明する README のセクションを書いて` |
| DevOps | `PR ごとに lint とテストを実行する GitHub Actions を作って` |
